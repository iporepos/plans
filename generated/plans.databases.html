plans.databases#

SQLite-based database classes for storing and managing hydro-environmental time series.

The base class DataBase structures a database around two table categories: catalogue tables (variables, flags, sources, statistics) seeded from shipped CSV files, and operational tables (specs, records) populated per project. SemiSpatialDB adds a feature_id to every record, for statistics on regular grids whose features are kept outside the database. SpatialDB is a GeoPackage file that also holds the features, in a features layer of any geometry type. Its children ZonesDB, PathsDB and SitesDB accept polygons, lines or points only, and records point to them by zone_id, path_id or site_id. SitesDB branches into FieldDB (in situ measurements), itself extended by HydrologyDB (river reaches with optional catchments) and DenseFieldDB (a wide layout for dense series), joined in HydrologyDenseDB, and LabDB (laboratory analyses of samples taken at the sites).

Table and column names are lowercase words joined by _; tables are plural, and a foreign key is the singular table name plus the target column (variable_name points to variables.name). In SemiSpatialDB, feature_id is the exception: it points to features outside the database.

A new database is created from a setup, given as a dict or as the path to a TOML or JSON file with the same structure:

[database]
path = "hydro.db"

[specs]
path = "my_specs.json"

[catalogs]
variables = "my_vars.csv"

{
  "database": {"path": "hydro.db"},
  "specs": {"path": "my_specs.json"},
  "catalogs": {"variables": "my_vars.csv"}
}

The specs file may be JSON or CSV, told apart by its extension. The catalogs section is optional, and omitted keys fall back to the shipped catalogs. Relative paths follow the working directory, not the setup file. Both formats refuse single backslashes, so Windows paths are written with forward slashes. SpatialDB adds a spatial section.

The specs table describes every dataset stored in records. A JSON specs file is a list of objects, one per dataset:

[
  {
    "name": "PPT_MONTHLY_CHIRPS",
    "abstract": "Monthly precipitation from CHIRPS v2.0",
    "method": "spatial average over catchment",
    "timestep": "1M",
    "extent": "catchment",
    "scale": 1,
    "offset": 0,
    "start": "1995-01-01",
    "end": null,
    "variable_name": "precipitation",
    "statistic_name": "sum",
    "source_name": "CHIRPS v2.0"
  }
]

Spec names are unique and uppercase (ASCII letters, digits and _, starting with a letter), so they never read like column names. Input names are stripped and uppercased, so ppt_monthly_chirps resolves to PPT_MONTHLY_CHIRPS. Public methods take spec_name (preferred) or spec_id; ids are only stable inside one database file.

Values in records are stored as stored = actual * scale + offset and returned as actual = (stored - offset) / scale. The records table has no uniqueness constraint on purpose: replicates at the same datetime are valid data (eg, three lab analyses on one day). Preventing a batch from being loaded twice is the job of the ingestion script, not of the database.

Each insert call is atomic and commits on its own. Several calls are grouped into one all-or-nothing block with DataBase.transaction():

with db.transaction():
    for name, df in batches.items():
        db.insert_records(dataframe=df, spec_name=name, flag=1)

Every record carries a flag from the flags table. By default, NaN values are not stored. With nan_policy="void" they are stored as NULL with the void flag (0), so a gap reported by the source can be told apart from data that was never loaded; NULL is the only placeholder, so SQL aggregates and pandas skip voids without extra handling. On insert, values outside the variable domain turn regular (1) rows into suspect (2): the value is kept, and a warning reports the count.

Flags of value 0 or below mean “no measured value” (void, not analysed, not applicable, not detected, …) and are the only ones that allow a NULL value; nondetect may instead hold the detection limit. Positive flags always carry a value (regular, suspect, raw, consisted). Censored records hold a limit, not a measurement, so analyses should filter by flag (eg, "flag_value": [1, 4]) rather than average everything.

Domain notation#

The domain column of variables holds the valid range of actual values as one or more intervals joined by U (union). Inside an interval, U separates the lower and upper bounds. [ and ] include the bound, ( and ) exclude it, and an empty bound is unbounded.

Values accepted

Example use

0 <= x

precipitation

(0U)

0 < x

strictly positive

[0U1]

0 <= x <= 1

[-1U1]

-1 <= x <= 1

NDVI

(0U1]

0 < x <= 1

[-273.15U)

-273.15 <= x

temperature in C

(U)

any value

no constraint

[5U5]

x == 5

Domains are checked when the variables table is seeded, so a malformed domain fails at database creation.

transaction()[source]#

Group several inserts into one atomic block.

The block commits on success and rolls back on any exception, which is re-raised. Blocks can be nested: a failed inner block rolls back only its own changes, and only the outermost block commits. Outside a block, each public insert commits on its own.

Do not call execute_sql() inside a block: executescript commits any pending transaction first.

Returns:

this database

Return type:

DataBase

Example:

with db.transaction():
    for name, df in batches.items():
        db.insert_records(dataframe=df, spec_name=name)

insert_records(dataframe, spec_id=None, spec_name=None, flag=None, columns_map=None, transform_values=True, nan_policy='drop', drop_extra=False, check_domain=True)[source]#

Insert records into the records table for a given spec.

The spec is given by spec_name (preferred) or spec_id and is broadcast to all rows in the batch. If both are given and disagree, spec_name is used and a warning is issued. The datetime column is converted from text to epoch seconds automatically. The optional linear transform (stored = actual * scale + offset) is resolved from the matching row in specs.

NaN in value follows nan_policy: "drop" skips those rows; "void" stores them as NULL with the void flag, overriding the batch flag, so a known gap can be told apart from data never loaded. Rows whose flag is already a no-value flag (0 or below, eg notanalysed) are kept as given under both policies.

With check_domain, actual values outside the variable domain (see the module notes on domain notation) turn regular rows into suspect and issue a warning. Values are kept; other flags are left as given.

Inputs are validated before anything is written: unknown flags, unparseable dates and columns records does not have raise an error.

Warning

Spec ids depend on the order specs were created, so the same id can point to different datasets in two database files. Prefer spec_name.

Parameters:

  • dataframe (pandas.DataFrame) – source data; must contain the columns in _RECORD_COLUMNS (datetime and value in the base class); flag_value is also required unless flag is provided

  • spec_id (int, optional) – id of the spec; used only if spec_name is None

  • spec_name (str, optional) – name of the spec (preferred); case is ignored

  • flag (int, optional) – if given, overwrite or create the flag_value column with this constant

  • columns_map (dict, optional) – column mapping {db_col: csv_name_or_index}; values may be a string (source column name) or an int (source column position, 0-based)

  • transform_values (bool) – apply linear transform if True

  • nan_policy (str) – for NaN values with a positive flag, "drop" skips them and "void" stores them as void records

  • drop_extra (bool) – drop columns records does not have instead of raising

  • check_domain (bool) – flag values outside the variable domain as suspect

Returns:

None

Return type:

None

Raises:

query_records(query_dict=None, quiet=True)[source]#

Query the records table with optional filters combined with AND logic.

Filters and options are passed as a single dict so the interface stays stable as new keys are added. All keys are optional; an empty or absent dict returns the full table. Unknown keys raise an error.

Filter keys:

  • spec_name (str or list[str]) — one or more spec names (preferred); case is ignored; wins over spec_id with a warning if both disagree

  • spec_id (int or list[int]) — one or more spec ids, used only without spec_name

  • start (str) — lower datetime bound (inclusive); any format parseable by pandas

  • end (str) — upper datetime bound (inclusive)

  • flag_value (int or list[int]) — one or more flag values to include

Option keys:

  • transform_values (bool, default True) — reverse the linear transform so value holds actual values via actual = (stored - offset) / scale

  • wide (bool, default False) — one column per spec, indexed by datetime

  • aggfunc (str or callable, default None) — with wide, aggregate replicates at the same datetime (eg, "mean"); None raises on replicates

  • with_meta (bool, default False) — add variable, units, statistic and source; as columns in long format, as df.attrs["specs"] in wide format

The long format is ordered by spec, then datetime, and carries both spec_name and spec_id. Without spec_name and spec_id, records of all specs are returned. datetime is always a timezone-aware (UTC) pandas datetime.

Warning

Spec ids depend on the order specs were created, so the same id can point to different datasets in two database files. Prefer spec_name.

Parameters:

  • query_dict (dict, optional) – filter and option keys (see above)

  • quiet (bool) – if False, prints elapsed query time to stdout

Returns:

matching records, in long or wide format

Return type:

pandas.DataFrame

Raises:

ValueError – if a key is unknown, aggfunc is given without wide, or wide meets replicates without aggfunc

Example:

        "spec_name": ["PPT_MONTHLY_CHIRPS", "Q_MONTHLY_ANA"],

Features are not stored in the database: feature_id is an integer key (eg, an H3 cell index or a grid cell id) that points to a layer kept elsewhere. Spatial selection happens outside, and the selected ids are passed to query_records().

class plans.databases.SpatialDB(name, alias=None)[source]#

Bases: SemiSpatialDB

GeoPackage database whose records point to features stored in the same file.

The file holds one layer of features next to the standard tables. Each feature has a generated id, a unique name, a geometry and the attributes declared in the columns map. Records carry feature_id, a real foreign key to the layer, so a record cannot point to a missing feature.

This class stores any geometry type, mixed in one features layer. Its children ZonesDB, PathsDB and SitesDB accept one kind only and rename the layer and key after it (eg, zones and zone_id). A child sets the layer name, the record key and the accepted geometry types; the SQL templates in sql/spatial are filled from them.

The layer is written and extended through geopandas only. Plain SQLite cannot insert into it, because the GeoPackage triggers call functions that only GDAL defines. All other tables work as in DataBase.

The setup adds a spatial section to those of DataBase.new(), and the database path must end in .gpkg:

[database]
path = "catchments.gpkg"

[specs]
path = "catchments_specs.json"

[spatial]
file = "hydrology.gpkg"

The file is the source of the features, in any format geopandas reads. The layer picks one layer of a file with several; without it, the first layer is read, with only a warning.

class plans.databases.DenseFieldDB(name, alias=None)[source]#

Bases: FieldDB

Field database in a wide layout, for dense and regular series (eg, hourly).

records holds one row per site and time, with one column per spec, instead of one row per value. The columns are created from the specs, each named after its spec in lowercase. Rows are stored by site and then time, so a station series reads fast, while one variable over all stations scans the table.

Values are regular unless record_flags says otherwise, so flags take no space until a value needs one. query_records() keeps its keys and output, without the id and inserted columns of the long layout.

Each spec loads on its own, in any order, into its column: a value fills the row of its site and time, which is created if missing. There are no replicates: a second value for the same spec, site and time raises. Specs cannot be added after creation yet.

Specs may mix timesteps. A coarse value sits on one row, and the rows between two values keep an empty cell, about one byte each: a monthly spec next to daily ones costs about 30 bytes per value, close to the long layout. This suits a few coarse specs next to many fine ones (eg, yearly land use next to daily series). Many coarse specs, or a step far finer than the rest (eg, monthly next to hourly), are better kept in a separate database. Coarse values should share the timestamps of the fine rows (eg, the first day of the month at 00:00), or each adds a row of its own.

records and record_flags are WITHOUT ROWID tables, which GDAL cannot open, so a GIS shows the sites and the catalogs but reads no records; they are read through query_records() or SQL. Queries build long rows in pandas, so one variable over all sites and all times takes memory in proportion; filter by site or time for large files.

  • alias (str, optional) – short alias

class plans.databases.LabDB(name, alias=None)[source]#

Bases: SitesDB

Sites database for laboratory analyses of field samples.

Data follows the chain sites -> samples -> mixtures -> records. A sample (eg, a water bottle) is taken at a site at a sampling time. The lab analyses a mixture of one or more samples; most mixtures hold a single sample, and a sample may enter several mixtures. Records carry mixture_id and the analysis time, which may be unknown (NULL). There is no aliquot table: the mixture stands for whatever the lab analysed.

Queries filter and sort by the sampling time (sample_datetime, the latest sample of the mixture) and return both times; the gap between them is how long the sample was stored. Filters by site_id or site_name match records whose mixture holds a sample from those sites, so a blend of two sites shows up under both.

Identical results are valid replicates (eg, a triplicate “not detected”); only the record id tells them apart.
